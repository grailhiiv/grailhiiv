## P1: forged asset metadata grants access to another client's file

Locations: `supabase/migrations/202610090003_atomic_import.sql:53` and `supabase/migrations/202610090002_storage.sql:5`.

`commit_records` checks the storage path only when the caller-supplied `uploaded` field is true. A team member can create an asset record for their assigned client with `uploaded: false` and a `storagePath` belonging to a different client. The storage read policy then trusts the new metadata record rather than independently checking the object's workspace/client path. The application Zod schema also permits this combination.

Reproduced in embedded PostgreSQL using the actual migrations: an unassigned client's object was initially invisible; it became visible after inserting the forged metadata. Reproduced against the configured live Supabase project using generated users and an isolated two-client workspace: the app accepted the forged metadata, `/api/assets/file` returned 302, and the signed URL downloaded the unassigned client's 68-byte test file with HTTP 200. The attacker needs to know the target object's path; knowing a path must not grant access.

Required repair: validate every non-null storage path independently of `uploaded`; prohibit storage paths on demo assets; ensure workspace and client folders match both metadata and current membership inside the storage read policy. Validate this at the database boundary as well as the API boundary. Add regression cases for another client and another workspace. Use a new forward migration on installed projects, not a rerun of installation migrations.

## P2: direct RPC calls can persist invalid post payloads

Location: `supabase/migrations/202610090003_atomic_import.sql:39`.

The API validates records with Zod, but authenticated users can invoke `commit_records` directly. PostgreSQL's `NULL NOT IN (...)` evaluates to NULL, so the conditional fails to reject a post with null status. Required post fields and types are not comprehensively enforced by the database RPC. Invalid records are then returned without validation by the workspace GET endpoint and can break screens that assume a string status.

Reproduced in embedded PostgreSQL and against the configured live Supabase project: a team member's direct RPC inserted a new post with `status: null` successfully.

Required repair: enforce required JSON fields and their types at the database/RPC boundary, including explicit null rejection and valid enums. Add malformed-payload tests that bypass Next.js entirely; do not rely only on API Zod validation.

## Not verified by this audit

Actual signup/invitation/recovery email delivery, custom SMTP configuration, HTTPS production deployment, backup/restore operation, exhaustive concurrent permission-revocation races, production load/rate limiting and all-device interoperability. The automated live browser check uses separate users/sessions rather than physical devices. AI, n8n and social publishing remain outside Phase 1 and unconnected. This is a bounded application audit, not a comprehensive penetration test.
